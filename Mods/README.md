# Railhead mods

Example mods for Railhead, built the way anyone outside the studio would build one: data only, on
the extension points the game exposes. The game never names them; it says only that mods live in
`Mods/` in its project directory (Project Settings > Plugins > Gantry Experience > Mod Directories,
with Mount Mods At Startup on). Each attaches under `Experience.Base` and **Extends**
`Experience.Coast`, so it rides along on every Coast Line stretch.

| Mod | What it shows |
|---|---|
| `Blizzard` | Weather from data. Its experience runs the game's **Weather** stage: a low white sky, falling light, snow on the ground and the track. The stage's Train Speed Scale slows the train through the line's speed hook, and the mod's own game feature carries a **Patch Data** action that makes the Coast Line's rails slippery (`DA_LineRules_Coast` Acceleration) while it runs. |
| `FreightVan` | A car from data. Its experience runs the game's **Couple Cars** stage with its own van, a Blueprint subclass of the game's car with its length, body and paint set. Shipped as one `.gantry` file and dropped into a running game, it joins at the next tunnel. |
| `LiveryCobalt` | Config only. Its experience activates the mod's own game feature, and the feature's config repaints the caboose cobalt blue (see Config, below). |

## Trying them

- **In the editor:** the editor never mounts mods at startup. Run `Gantry.Mods.Mount` at the
  editor's console, then play; an uncooked run reads each mod's loose content directly.
- **In a packaged game:** each mod needs its cooked containers in `Content/Paks/<Platform>/`. They
  are not in the repository, so cook the mods first (see Cooking against a release, below).

## Mods with problems

`ModsWithProblems/` holds two more, outside the game's mod directories so ordinary runs never see
them. Add `ModsWithProblems` to Mod Directories and mount to see Gantry deal with them:

| Mod | What happens |
|---|---|
| `LiverySaffron` | Sets the same livery key as `LiveryCobalt`. Gantry reports the clash: whichever activates last paints the caboose. |
| `LocomotiveMkII` | Made for a newer game: its game feature data needs game version 2.0. Gantry registers it, finds it incompatible, and unmounts it again, saying why. |

## Config

A game feature's config changes go in `Config/<Mod><Branch>.ini`: `LiveryCobaltGame.ini` for the
Game branch. When the feature activates, the engine layers that file over the game's own config.
It applies nothing else from `Config/` then; a `DefaultGame.ini` there is never read, and Gantry
notes it on the mod. `Config/Tags/` is read when the mod is registered, so mods bring their own
experience tags.

## What the game offers mods

Railhead declares what a mod may build on, and Gantry writes it down:

- **`Config/DefaultGantryAPI.ini`**, generated by the editor when it starts and when a cook begins
  (and by `-run=GantryAPI`), lists the
  classes, properties and functions marked `GantryAPI` in the source, and the channels the game
  declares. A JSON copy lands in `Saved/GantryAPI/` for tools. The API version is 1.0; a mod can
  ask for a range in its game feature data (Required API Version).
- **Channels.** `Railhead.Message.Line.Tunnel` and `.Daylight` announce the tunnels;
  `Railhead.Hook.Line.Speed` is a hook the server runs every tick with the speed the train heads
  for, and any listener may change it. The game's module declares all three; with Warn On
  Undeclared Channels on, anything sending on a channel nobody declared is logged.
- **Stages.** The **Couple Cars** stage couples a mod's own cars to the train; the **Weather**
  stage lays weather over the line and, through its Train Speed Scale, listens to the speed hook.
- **Config.** The `[/Script/Railhead.RailheadLiverySettings]` section: a mod's
  `Config/<Mod>Game.ini` repaints the caboose.
- **Components.** The line and the train take components from game features. Gantry registers
  them as receivers (Automatic Receiver Classes), so neither registers itself. No example mod
  uses this yet.
- **Data patches.** A mod's game feature can change the game's data values and table rows while it
  is active, and Gantry puts them back after. Two mods patching one value are reported.

## Turning mods off

Settings > Mods lists every mod found, with a toggle each; only the first player has the page,
since mods belong to the machine. A mod turned off stays in `Mods/` and is not loaded (nor is
anything that builds on it); the choice is the player's, kept in
`Saved/Config/<platform>/GantryMods.ini`. `Gantry.Mods.Disable <Mod>` and `Gantry.Mods.Enable <Mod>`
do the same from the console.

## Code

These mods carry no code, so they work in every build of the game. A mod with C++ modules needs a
game that can load code from a plugin: the editor, or a game built modular from a source engine,
with the mod built against that exact build. A packaged game is normally a single executable, and
there Gantry refuses a mod with modules before mounting anything of it.

## Cooking against a release

As for any Gantry game: package the game with `-createreleaseversion=<release>`, then cook each mod
with the stock BuildCookRun (`-cook -stage -pak -dlcname=<path to its .uplugin>
-basedonreleaseversion=<release>`, plus `-target=GantryCodeExampleServer -server -noclient` or
`-target=GantryCodeExampleClient -client` for dedicated builds). The staged containers go in the
mod's `Content/Paks/<Platform>/`; copy the mod folder (`.uplugin`, `Config`, `Content/Paks`) into
the packaged game's `Mods/`, or zip it, stored, as `<Mod>.gantry` and drop that in.

## Playing with mods over the network

Every machine needs the same mods, in the same version. A client without a mod the host runs, or
with another version of it, cannot ride that stretch: Gantry refuses it with a reason naming the
chains (or the mod and both content ids), and Railhead shows it with the way back to the main
menu. A mod's content id is the same for every platform and server or client cook of the same
source, so a Linux server and a Windows client agree.
